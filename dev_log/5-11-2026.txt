User picks (questions asked before sleep):

- End-of-game UX: Modal overlay
+ user note: "Tactical battles sure, but not just fight for
  the sake of it. Resource, economy, upgrades to units, etc
  to come. Don't forget the big picture."

Big-picture design intent (per the user's note): build
this nail so that adding future systems (resources, recruit-
ment, upgrades) means adding fields to existing structures,
not rewriting them. Hence:
- Nation type holds all per-faction state in one place
- Region ownership tracked explicitly (Int16Array) — not
  derived from "who has an army here." A region the AI just
  expanded into stays AI-owned even when their army moves on.
- Capital tile is a real coord (not an abstract concept) so
  capital-occupation is first-class.

Files

nation.ts (NEW):
  Nation interface. Fields: id, color, capitalRegionId,
  capitalX/Y, army (or null if destroyed), isPlayer,
  eliminated, nextDecideAtMs (AI), lastSiegeResponseAtMs,
  captureProgress (the active capital hold this nation is
  currently performing, if any).

gameModal.ts (NEW):
  VICTORY/DEFEAT modal. show(kind, subtitle) and hide().
  Title color via [data-kind] CSS rule (gold for victory,
  red for defeat). NEW MAP button calls onRetry.

army.ts:
  - ArmyDeps gained homeRegionId + color. createArmy uses
    these instead of world.playerRegionId (was a coupling
    assumption that only worked for one army).
  - New marchTo(x, y) method: programmatic march for AIs.
    No neighbor-region validation (caller's responsibility).
  - New isMarching(): bool for AI decision gating.

mapRender.ts (rewritten):
  Takes regionOwner Int16Array + nations[] now. Tints follow
  ownership: player gets PLAYER_TINT_ALPHA (0.55) of their
  color; AIs get AI_TINT_ALPHA (0.38); neutral regions get
  NEUTRAL_COLOR (0x8b8d92) at NEUTRAL_TINT_ALPHA (0.18).
  Capital markers: one per nation (not per region), color
  follows current owner. Player's main capital gets the big
  glyph + white ring. New exported rebuildOwnerLayers()
  redraws tint + player + capital layers on ownership
  change. Borders are static (drawn once at build).

main.ts (major rewrite):
  Replaces let army + let enemy with let nations: Nation[].
  Loads via single loadMap(seed) path (no separate init-vs-
  load divergence). All combat / capture / AI logic operates
  on the nations array.

  Setup helpers:
   - pickStartingRegions(world, count): player gets the
     largest region; subsequent picks maximize min-distance
     to all already-picked. Gives 3 well-spaced spawns.
   - rollComposition(rng): unchanged from #6.2 follow-up #4
     (40-100 soldiers, 10-50% cav).
   - spawnNations(world, seed): creates Nation[] using a
     dedicated RNG stream from seed ^ 0x9e3779b9 (same
     pattern as #6.2 follow-up #4).
   - initRegionOwner: fills Int16Array with -1 except for
     each nation's capital region.

  Battle state machine: unchanged conceptually, but now
  references activeOpponent: Nation | null instead of a
  singleton enemy. battleMenu wiring + simulateBattle calls
  read activeOpponent.army.getRegiments() etc.

  AI behavior (tickAi):
   - Every ~10s (jittered ±2.5s), if their army is idle and
     they're not currently sitting on an enemy capital, pick
     an expansion target.
   - Target selection: prefer neutral neighbors of any owned
     region; fall back to enemy-owned. Random within the
     preferred pool.
   - Fight-back: if any other nation is currently capturing
     this nation's capital (isSiegedBy returns non-null),
     skip expansion and march army home instead. Re-issue
     the home march every 2s while siege is active.
   - "Sit on enemy capital" guard: if this AI is currently
     within capital-hold radius of an enemy capital, skip
     this decision cycle so the capture timer runs out.

  AI vs AI battles (resolveAiVsAiBattle):
   - Triggered from tickEngagements when two AI armies meet.
   - Runs simulateBattle silently, applies casualties,
     destroys any army that hits zero.
   - showAiBattleIcon flashes a small crossed-swords mark at
     the engagement midpoint for 1.2s, fading out. The icon
     lives on a dedicated aiBattleIconLayer above the
     strategic layers.

  Symmetric capital occupation (tickCapture):
   - Per-nation. If a nation's army is within CAPITAL_HOLD_
     RADIUS (24wu) of a non-self-owned capital, that nation's
     captureProgress kicks off.
   - Same target across frames → progress accumulates;
     change target / leave radius → reset.
   - After CAPITAL_HOLD_MS (15s), captureCapital fires:
     flip ownership of the captured nation's capital region
     AND all their other regions to the captor; destroy the
     captured nation's army; mark them eliminated; rebuild
     ownership-driven layers; check game-over.
   - Player can't capture during combatState === 'engaged'
     (the battle freezes them). AIs in silent battles aren't
     frozen meaningfully — battles resolve in one frame.

  Region claim on arrival (tickRegionClaims):
   - When a non-eliminated nation's army stops (no longer
     marching) in a region that is neutral, the region flips
     to that nation. Enemy-owned non-capital regions don't
     auto-flip — they stay contested until the owner is
     eliminated via capital capture. (Future nail: port.md's
     full per-tile claim with the 30-tick timer.)

  Win/defeat (checkGameOver, called from battle exit +
  captureCapital):
   - Defeat if player.army is null/empty OR player capital
     is owned by another nation.
   - Victory if all non-player nations are eliminated.
   - Either fires gameModal.show with the appropriate kind.

  Readout (expanded):
   - Shows current combat / capture / siege status. New
     branches: '>>> CAPITAL UNDER SIEGE by #X (Ys) <<<' when
     someone's besieging the player; 'enemies: #1 #2' when
     idle. Game-over states also surface in the readout.
   - Readout re-renders every frame the player is besieged
     (so the countdown ticks) — gated to avoid full re-render
     spam otherwise.

  Ticker order each frame:
   1. Per-nation army.tick(dtSec) — except player + active
      opponent are frozen during combatState === 'engaged'.
      Other AIs keep moving.
   2. tickAi — expansion decisions.
   3. tickEngagements — pairwise contact check; player vs
      AI opens menu, AI vs AI resolves silently.
   4. tickRegionClaims — neutral region pickup.
   5. tickCapture — symmetric capture progression.
   6. tickBattleSystem — pre-roll / transition / menu.
   7. Camera transform + view-tier + readout throttling.

index.html:
   - New #game-modal overlay with .card containing
     #game-modal-title (data-kind="victory"|"defeat" drives
     color), #game-modal-sub (subtitle), #game-modal-retry
     (NEW MAP button).
   - High z-index (20) so it overlays the battle menu.

2026-05-11 (later) — nail #6.4: recruitment

User asked "what's next" after #6.3 shipped. Picked
recruitment as the next nail. Key user notes:
- Recruit rate should scale with what's built on the tile
  (buildings/upgrades to come). For now, baseline +1/capital
  but architecture must support per-capital modifiers.
- Player picks unit type. Time proportional to strength.
  Will rebalance once tactical battles ship.
- Army cap scales with regions (50 + 10/region).

Design decision I made + flagged: defeat condition was
"army destroyed OR capital captured" pre-recruitment. With
recruitment regrowing armies, the "army destroyed" path
fires immediately after a battle wipe and would race
recruitment. Relaxed to capital-captured-only.

Implementation summary in v2.me. Key TDZ check: addSoldier
calls Army.respawnAt() only when transitioning empty→non-
empty. Mid-march armies with surviving troops keep their
position and just gain a recruit at current location. Wiped
armies (regiments=[]) move to capital on first recruit.

The recruitment-rate function is the planned extension point
for buildings:

  function getRecruitmentRate(n) {
    if (n.eliminated) return 0;
    return ownedCapitalCount(n.id) * RECRUIT_RATE_PER_CAPITAL;
  }

Future building nail can change this to:

  function getRecruitmentRate(n) {
    if (n.eliminated) return 0;
    let r = 0;
    for (const cap of ownedCapitals(n)) {
      r += RECRUIT_RATE_PER_CAPITAL;
      for (const b of cap.buildings) r += b.recruitBonus;
    }
    return r;
  }

Shape stays stable; only the body grows. Same hook fits
resource yield later.

What I want eyes on:
- Does the recruitment % feel right? At 1/cap baseline,
  recovering from a 20-soldier loss takes 20s if recruiting
  inf. Too slow?
- Does the cap-by-region incentive feel like real strategic
  pressure to expand?
- UI: the "recruit: INF" toggle button under "new map" works
  on phone? 44px tall.
- Readout: the new recruit line ("recruit: inf 45% · 60/60 ·
  1.0/s") readable at 12px monospace?
- AI vs AI dynamic: AIs now recover from battles. Lost-army
  AI marches home (fight-back logic), gets recruits, fights
  back. Should feel like an alive opponent.

2026-05-11 (later still) — mid-game region capture

User flagged after playing #6.4: "I can't capture enemy
non-capital regions, right?" Correct — that was a deliberate
"future nail" punt in #6.3 (the comment in tickRegionClaims
called it out). Without it, gameplay was binary: nibble
neutrals or rush the capital.

User picks: hold-based capture (like capitals but faster);
combat naturally resets the timer (enemy in range cancels
hold); no adjacency requirement (anywhere your army can
march is fair game); AIs symmetric. Also asked for capital
hold dropped 15→10s.

Implementation: extended tickRegionClaims with a third
branch. Neutral still flips instantly. Enemy capital still
routed through tickCapture (so the capital-capture cascade
flips all their regions at once — that mechanic is
preserved). Enemy non-capital: start a 5s hold; reset if
enemy army comes within COMBAT_TRIGGER_RADIUS. Symmetric
for all nations.

Tuning constants now:
  CAPITAL_HOLD_MS = 10_000  (was 15_000)
  REGION_HOLD_MS  =  5_000  (new)

Open follow-ups:
- AI doesn't actively defend regions under siege (only
  capitals trigger fight-back). If this feels too easy,
  add region-defense AI.
- No visual ring on regions being captured (capitals get
  the ring; regions don't). Could add a pulse or border
  flash. Polish.

2026-05-11 (even later) — long-range player movement

User: "not able to move to a tile that's not next to me,
I should be able to move across the map so long as my path
doesn't go through enemy land (unless I'm at war with them)
and our tiles are attached."

Also mentioned: future state is multiple armies per nation.
Flagged for later — not refactoring Nation.army → armies[]
now. Pathfinder is per-call and per-army, so the change
will be additive when we do it.

Implementation: BFS through region graph at drop time.
Passability rule:
  - source / destination region: always passable
  - any other region: must be owned by player or neutral
  - enemy regions block transit but are OK as the
    destination

If no path: drop rejected, previous march resumes (same
behavior as old reject path).

Army's march field went from single { toX, toY } to a
waypoint queue { waypoints[], idx, targetRegionId }. Tick
advances through waypoints. Polyline drawn through
remaining points. marchTo (AI single-target) wraps to a
one-waypoint march, so AI call sites are unchanged.

Going with the permissive rule (neutrals OK as transit).
Reason: user said "doesn't go through enemy land," not
"only through my land." If they meant stricter, easy to
flip the predicate (drop the `owner < 0` clause).

AI asymmetry note: AIs straight-line. Doesn't enforce the
same transit rule on them. If this feels exploitable in
practice we can wire pathfindForNation into marchTo. The
infrastructure is there.

The transit predicate is the war/alliance hook for future:
  passable = nb === to || owner === nationId || owner < 0
            || alliedWith(nationId, owner)
            || atWar(nationId, owner)  // enemy passable
            ...
