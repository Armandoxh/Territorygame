[a51395f] gameplay: aura BFS-foothold so claims actually radiate
from the army (not the empire's whole frontier)

WHAT: Previous aura scanned a 21×21 box and claimed any non-owner
tile that touched ANY of the player's tiles. For an army inside
a big empire, that bubble overlapped a long stretch of the
existing empire frontier — claims appeared all along that
frontier, looking like the legacy flat flood.

Replaced the box-scan with BFS from the army's tile through
OWNED tiles, bounded to ARMY_AURA_RADIUS=10 cardinal hops.
Foothold = owned tiles reachable from army within R hops.
Candidates = non-owner cardinal neighbors of any foothold tile.

Result:
  - Paratrooper on neutral land → foothold-step claims drop tile
    → BFS finds candidates at 4 cardinal sides → web grows
    concentrically from the drop point.
  - Army deep in own empire → BFS fills R hops, no non-owner
    neighbors → candidates empty → no aura claims (army is
    "settled"; user moves it elsewhere). Strength still regens.
  - Army at the empire's edge → BFS fills locally → claims only
    along the edge near the army, not 30 tiles away on the other
    side of the empire.

WHY: User: "It's not expanding to that land it's attacking, it's
more like a flat expansion of my territory across the board. Do
the expansion around that army itself."

Cost: BFS bounded by R=10 ≈ 100-300 visited tiles per army-tick.
At 20 armies total, ~5000 ops/tick — well within budget at 10Hz.

[uncommitted] v2 commit B: dual-scale zoom on placeholder grid (Nail #1)

WHAT: Five new src/ files inside swarm/.

  camera.ts (~30 LOC)
    Plain object — zoom, panX, panY. Two methods.
    zoomAt(factor, sx, sy, vw, vh) clamps the new zoom into
    [minZoom, maxZoom] then adjusts pan so the world point that
    was under the cursor/finger stays under it (focal-point
    zoom). panBy(dxScreen, dyScreen) translates pan in world
    space (dx/zoom).

  placeholder.ts (~50 LOC)
    50x50 grid. cellColor(x, y) hashes (x*12.9898 + y*78.233) →
    deterministic 3-color pattern: 10% water, 15% sand, 75% grass.
    Strategic layer: 2500 rect fills in one Graphics.
    Detail layer: 51+51 grid lines (1px stroke, alpha 0.45) +
    2500 center dots (r=2, alpha 0.6). detail.alpha=0 at start;
    main.ts drives it from camera zoom.

  input.ts (~60 LOC)
    pointerdown/move/up/cancel + wheel + keydown.
    Pointers tracked in Map<id, {x,y}>. On pointermove: 1 active
    → camera.panBy(dx, dy). 2 active → recompute pinch distance,
    factor = newDist/oldDist, zoom around midpoint of two
    pointers. lastPinchDist resets when count drops below 2.
    Wheel: factor = 1.0015^-deltaY (smooth on trackpad,
    snappy enough on click-wheel). Keyboard: +/- → 1.2x / 0.83x
    around screen center.
    setPointerCapture so drags don't drop when finger leaves
    canvas. preventDefault on wheel so the page doesn't scroll.

  store.ts (~12 LOC)
    Zustand vanilla store with { zoom, view, crossfade }. view
    is 'STRATEGIC' | 'MID' | 'TACTICAL'. Subscribed by the DOM
    readout. Per-tick setState gated by a deadband (crossfade
    delta > 0.01 OR view changed OR zoom delta > 0.001) so we
    don't churn 60 times/sec on idle.

  main.ts (rewritten, ~70 LOC)
    Constants: TILE_SIZE=32, CELLS_X=CELLS_Y=50 (so world is
    1600x1600). Initial zoom fits the grid in viewport with
    a 0.9 margin; minZoom = initialZoom*0.5, maxZoom = 8.
    Per-frame: world.scale.set(zoom); world.position.set(
    vw/2 - panX*zoom, vh/2 - panY*zoom). Crossfade from
    cellPixelSize: 0 below 24px, 1 above 64px, linear between.
    Push to store with deadband. DOM readout shows
    "swarm v2 — zoom 1.20x — STRATEGIC→TACTICAL 40%" or similar.

WHY: Nail #1 done end-to-end. Per the mantra ("nail one aspect
before moving to the next"), this is the *only* thing — no map
gen, no soldiers, no selection, no anything else. Once user
thumbs-up on phone, the next nail (probably map gen at the
strategic scale, replacing the hashed-color placeholder) opens.

Bundle: ~210 KB gz total. typecheck clean. Build clean. No
lint, no tests — lean per the constraint. If pinch feels jumpy
on phone we add target-lerp smoothing in a follow-up; shipping
without it first to know whether smoothing is needed.

[uncommitted] v2 Nail #2: procedural map gen + strategic render

WHAT: Replaced the 50x50 placeholder grid with a 100x100
procedural world.

  world.ts (~140 LOC, pure data, no Pixi)
    Mulberry32 RNG seeded by opts.seed (currently 1337 — fixed
    for reproducibility this nail). Bilinear value-noise on a
    coarse cell grid: two octaves at freq 14 and 6, weighted
    0.6/0.4. Radial continent falloff (1 - distance-from-center)
    + (noise - 0.5) * 0.85. Threshold 0.18 → grass/water binary.
    Sand pass: every grass tile with any cardinal water
    neighbor becomes sand. Region seeds via rejection sampling
    on land with min-spacing of sqrt(area / regionCount) * 0.6.
    Multi-source BFS with neighbor-order shuffle (per-pop
    Fisher-Yates) so boundaries are slightly noisy. 25 regions.
    Placeholder owner colors: HSL with hue = (idx * golden) % 1,
    S=0.55, L=0.55 → distinct adjacent colors.

  mapRender.ts (~70 LOC)
    Three Graphics layers built from a World:
    - terrain: rect.fill per tile (water 0x3a6090, sand 0xc9b070,
      grass 0x4a7a3e). Always alpha 1.
    - tint: rect.fill per land tile at region.color, alpha 0.55.
      Visible at strategic, fades at tactical.
    - borders: stroke along right/bottom edges where regionOf
      differs (covers region-vs-region AND land-vs-water).
      Single stroke({ width: 1.5, color: 0x111111, alpha: 0.85 })
      after all subpaths emitted. Visible at strategic, fades at
      tactical.

  main.ts (rewritten, ~85 LOC)
    Constants now at top: TILE_SIZE=16, WORLD_TILES_X=Y=100,
    REGION_COUNT=25, WORLD_SEED=1337. World is 1600x1600 world
    units (same physical size as the 50x50 * 32 placeholder).
    Adds three layers in order: terrain, tint, borders.
    Crossfade now: at strategic (cellPixelSize <= 24), tint+border
    alpha = 1; at tactical (>= 64), alpha = 0; linear between.
    Readout extends to "... — N regions" so we can sanity-check
    gen succeeded.

  Deleted: placeholder.ts (no longer used).

WHY: Per the mantra, Nail #2 = the next single aspect from
port.md's milestone list ("Map gen: ~150x150 tile world,
regions, water/land, capital placement"). Stayed scoped:
terrain + regions only, no capitals, no soldiers, no AI yet.
World is 100x100 not 150x150 (user picked Medium for
phone-friendliness). Visual identity at strategic locks first
(lesson #1: visual style locks the engine) before any units
sit on top of it.

Bundle: ~220 KB gz total (main entry 74 KB gz). Typecheck
clean, build clean. Awaiting user thumbs-up on phone before
Nail #3.

[uncommitted] v2 Nail #4: region adjacency graph (data only)

WHAT: Two files.

  world.ts:
    - Region interface gets `neighbors: number[]` — sorted,
      unique region ids that share a tile-edge.
    - New generation step (between centroids and player-pick):
      build a Set<number>[] sized to regions.length; sweep
      every land tile and check its +x and +y neighbor; if
      both are land and have different region ids, add each
      to the other's set. Single pass, no double-counting.
      Flatten to sorted arrays at the end.
    - Player-pick step renumbered 6 -> 7.

  main.ts: readout appends "(borders N)" to the your-nation
  line, where N = playerRegion.neighbors.length. Smoke test
  that the graph populated.

WHY: This is the data spine for every future multi-region
system — army movement caps to adjacent regions, vassal /
diplomacy graph traversal, AI threat assessment ("how many
hostile neighbors do I have?"), expansion targeting. Worth
landing as its own atomic nail because it's invisible: if we
bundled it with capital markers or armies, a bug in the graph
would be hidden by the visual noise. Now if "borders N" reads
0 or 25, we know immediately.

Design call from user: edge-only (4-way) over 8-way. Matches
the boundary lines we render today; avoids corner-touch false
positives. Coastal / cross-water adjacency deferred until we
have naval pieces to use it.

Build clean, typecheck clean. Awaiting visual confirmation
the readout shows a sensible "borders N" (1-6 for an interior
region; could be 1-2 for a peninsula).

recreated on `loadMap`, so input needs to re-fetch the live
handler each pointerdown. While dragging, additional pointers
are dropped entirely — pan and pinch are locked until release.

all the existing pan/zoom paths.

  the formula manually.

[uncommitted] Nail #5b refinement: drop-position + march animation

Two user requests landed together:
1. "Bring it to where I drop it" — not the destination
   capital. Drop point IS the new position.
2. "It just teleports there? It should be a march of sorts."
   — animate movement instead.

Clarifying questions answered before coding:
- Mid-march re-grab → REDIRECTABLE. Drag-while-marching pauses
  movement; new drop = new march from current paused position.
- March speed → SLOW (30 world units/sec; ~6s per neighbor
  hop). Helps establish scale on a 1600×1600 map.

army.ts rewritten:
- Position is now continuous world coords (`pos: {x, y}`), not
  a regionId. Region is derived (`regionAt(pos.x, pos.y)`).
- `march: { toX, toY } | null` holds an in-flight destination.
  When non-null, tick() advances pos toward it by SPEED * dt
  per frame.
- New API: `tick(dtSec)` (called from Pixi ticker), `getStatus()`
  returns `{ marching, regionId, targetRegionId }`.
- Two separate Graphics for the line overlays: `dragLine`
  (white solid, while user is dragging) and `marchLine` (white
  faint, passive indicator from current pos to march target).
  Visually distinct so re-grab during march reads correctly.
- endDrag now returns boolean (committed vs cancelled). On
  cancel I deliberately do NOT clear `march` — the in-flight
  destination is preserved, so the army resumes after an
  invalid release. Matches the "redirectable" mental model:
  cancel = "never mind", not "abort".
- Same-region drops are accepted. The placeholder rule isn't
  "must change region", it's "must drop on land in current
  region or a neighbor".

main.ts:
- Ticker now calls `army.tick(deltaMS / 1000)` each frame.
- Readout cache (`lastArmyMarching`, `lastArmyRegionId`,
  `lastArmyTarget`) prevents per-frame re-render; only re-runs
  renderReadout when one of these changes. loadMap resets the
  cache.
- Readout text:
  - Stationary: "army @ home · drag to march" or "army @ #N · …"
  - Marching:   "army marching → #N"

Build + swarm typecheck clean (root typecheck shows v1 errors
in client/ that are unrelated; swarm uses its own tsconfig).

Awaiting visual confirmation:
- Drop on a neighbor → army glides to the EXACT drop point
  (not the capital), at a slow walking pace.
- During march, grab the army → it pauses where it is.
  Drag and release on a different neighbor → new march
  starts from the paused position.
- During march, grab and release on water/non-neighbor →
  release does nothing; march resumes toward original
  destination.
- Drop within your own region → march within current region
  (same animation, same pace).
- Faint march line connects current pos to destination during
  motion.
